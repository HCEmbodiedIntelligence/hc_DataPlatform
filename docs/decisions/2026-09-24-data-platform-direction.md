# 数据平台对比与下一阶段方向

日期：2026-09-24。用于需求决策；覆盖采集、存储、分段、质检、标注、UI 和交付，**不涉及训练**。本文区分已核实事实与建议，生产平台尚未切换存储。

## 1. 方向与结论

**确定方向：新标准化数据停用 Lance，直接保存为标准 LeRobot 文件；保留原始录制、现有 Tag 修订审核和业务数据库。**

建议每个 episode 版本形成可独立读取、下载的文件夹，UI 围绕这一条数据集中呈现来源、文件、质检和标注。学习对方的文件组织与语义展示，保留我们的编辑、版本和追溯能力。

| 需要明确的判断 | 结论 |
|---|---|
| 对方是不是 MCAP → LeRobot？ | 已核实是 MCAP → **SRobot**，含对齐、字段整理和动作处理；原包不能直接等同于官方 LeRobot。 |
| 对方没有数据库、我们把数据都放数据库？ | 两个判断都不成立：对方有任务/状态/版本等业务记录，数据库实现未知；我们的原件、媒体和 Lance 数据在对象存储，PostgreSQL 管业务及标注修订。 |
| 我们是否没有导出能力？ | 已有原始/已处理/已标注导出和按 episode 选择；短板是数据分散、取包和理解成本高。 |
| 能否直接改成文件存储？ | 已有官方 reader 原型证明可行；正式替换还涉及处理、读取、版本、标注和历史迁移。 |
| 是否要把 MinIO 换成 OSS？ | 没有此必要性证据；当前 MinIO 也可实现目标目录与文件包。 |
| 对方整体更好吗？ | 文件查看和语义结果展示值得学；在线标注闭环、性能、成本和可靠性不能据此判优。 |

本文件取代早期“保留 Lance、只加导出视图”的建议；SRobot reader 的结论以本次实测为准。证据链接集中在第 9 节。

## 2. 双方现状与优缺点

### 2.1 当前流程与存储

| 项目 | 我们当前 E 平台 | 对方已核实情况 |
|---|---|---|
| 采集与处理 | 明确开始/停止 → 原件封存上传 → 预览/切片 → episode QC、对齐和媒体处理 → Lance | 原始 MCAP 保留 → 转换成 SRobot 文件包 → 自动质检、人工数据审核；已有标注结果另行关联 |
| 原始文件 | `raw/<组织>/<项目>/<任务>/<机器人>/<upload_id>/` 下有 MCAP、视频、配置、清单、字段/封存说明及有效性事件 | 独立原始桶，按日期/机器人/任务/会话组织；`processes/<进程>/topics/<topic>/*.mcap`，附会话与相机说明 |
| 标准数据 | 分布在 `derived-recordings/`、`aligned-media/`、`lance/`、`derived/`、`artifacts/` | 一条 SRobot 目录集中放 Parquet、RGB MP4、深度 MKV、info、任务/子任务、模态、标定、转换报告 |
| 标注与审核 | Tag 编辑 → 不可变修订 → 固定提交 → 审核；PostgreSQL 保存修订、状态和业务关联 | processed 桶中已见版本化 COT JSON、EGO rebuild 包；不能据此推断完整人工编辑流程 |
| 导出 | 原件可下载；已处理数据可导出；已标注导出页无需用户先手动发布版本 | OSS 浏览器可预览和下载当前文件；整包/批量下载能力未完整验证 |

对方 `s-robot-raw` 桶中的样本已经转换，真正原件在另一个桶。以上文件模式来自多个样本，不表示每条数据都包含全部文件。

**我方完成度：**原始上传、切片、QC、实际 Lance 写入、Tag 提交/审核、LeRobot 导出和 reader 已有真实服务软件闭环；最新完整样例为两个各 6 帧的合成 episode，并有处理回执重放证据。真机、长数据规模和真人页面全流程仍需验收。机器人默认上传原件，上传前不是 LeRobot；切片先确定来源窗口，也不等于处理已完成。

### 2.2 优缺点与取舍

| 维度 | 对方 | 我们 | 决策建议 |
|---|---|---|---|
| 直观查看 | 单条目录按日期/设备/任务组织，数据与说明集中；大量目录仍需检索索引 | 稳定 ID、业务关系清楚，但一条数据跨多个存储位置 | 独立 episode 包 + 集中详情；人可读名称与稳定 ID 分开 |
| 离线交付 | 文件容易带走，但 SRobot 需要适配 reader | 已有标准导出，但它主要是派生产物 | LeRobot 成为主存储；已就绪包直接下载 |
| 来源追溯 | 转换报告直观；已查短文件没有更早裁切来源链 | 有原始录制、时间窗、版本、回执与重放；页面呈现分散 | 保留来源契约并在 UI 展开父录制与时间窗 |
| 标注 | COT/EGO 语义展示丰富，结果文件可检查；在线编辑闭环未证实 | Tag 层级、属性、对象/关系、修订、并发处理和审核已有基础；专门语义表单不足 | 保留编辑机制，增加步骤卡片、结构化字段及标注文件交付 |
| 规模与成本 | 独立包增加小文件、请求和元数据；不能仅凭目录判断快慢 | 已有帧查询/索引抽象，但依赖 Lance | 去 Lance 后用 Parquet、媒体索引、受控缓存承接必要查询；同源实测后优化 |
| 存储部署 | OSS 承载对象文件 | 当前 MinIO 同样可承载目标方案 | 优先改组织与流程；不因目录差异更换供应商 |

**需要解决的三个问题：找齐一条数据、离线能读取、日常下载少步骤。**没有同源性能/成本测试，不宣称任何一方更快、更省空间或更可靠。

## 3. 原始 MCAP 里到底是视频还是照片

**RGB 本质上保存的是视频编码流，没有逐帧保存成 JPEG/PNG 照片文件；深度是逐帧压缩的数值数组。**MCAP 是外层记录容器，消息内有时间戳和编码载荷；它不等于 MP4 文件容器。

| 实读流（样本 31247） | 原始 MCAP 消息中的内容 | 分辨率（宽×高） | 转换后的 SRobot |
|---|---|---|---|
| 头部 RGB | Protobuf `CameraEncodedVideoFrame`，`codec=h265`；H.265/HEVC 视频数据包 | 640×480 | H.264 编码的 MP4 |
| 左鱼眼 RGB | 同上，H.265/HEVC 视频数据包 | 1920×1536 | H.264 编码的 MP4 |
| 头部深度 | Protobuf `CameraDepthFrame`，`encoding=zstd_z16`；Zstd 无损压缩的 uint16 单通道数组 | 640×480 | FFV1 编码、gray16le 的 MKV |

验证：三条流各检查 312 条消息，RGB 实际解码通过；深度全部解压成功，每帧 `640×480×2=614,400` 字节。原始深度帧 25 与输出 MKV 首帧逐像素一致。其他流的原始编码与深度物理单位未逐一确认；相机元数据及输出媒体显示头部/双腕为 640×480，三路鱼眼为 1920×1536。

两步转换要分清：

- **原始 MCAP → SRobot：**RGB 从 H.265 变为 H.264 MP4；深度从 Zstd 数组变为 FFV1 MKV，不能理解成仅改文件后缀。
- **SRobot → 本次 LeRobot 原型：**复制已有 RGB MP4，没有再编码，文件哈希一致。“没有重编码”仅指这一步。

深度虽然逐帧保存为二维图，但不是 JPEG/PNG 照片，也不能当普通彩色视频处理。详细消息、解码起点和来源见[原始相机格式报告](../../../../diagnostics/simpleclaw-review/download-audit/raw-camera-formats.md)。

## 4. 录制、episode、subtask 与标注

### 4.1 长短数据怎样对应

| 样本 | 原始消息跨度 | SRobot 首末帧跨度 | 已确认关系 |
|---|---:|---:|---|
| 31247 | 10.400 秒 | 9.500 秒 | 独立短原始会话 → 一个短 episode |
| 31191 | 22.314 秒 | 21.567 秒 | 独立短原始会话 → 一个短 episode |
| 33809 | 87.664 秒 | 86.600 秒 | 一个长 episode，内部六个 subtask |
| 另外两条长会话 | 103.801 / 65.725 秒 | 102.900 / 64.967 秒 | 转换元数据均为一个 episode、六个 subtask |

首末帧跨度不含末帧显示区间；33809 的视频播放时长约 86.633 秒。对齐、裁边和帧处理会造成输出略短，不能因此认定拆成了新任务。

审核页抽查的 10～20 秒记录是独立 episode，引用各自原始目录；短样本采集起止清单更支持独立短录制。**尚未找到有来源链支撑的“同一长 MCAP → 多个独立短 episode”实例，不能断言对方从未使用这种流程。**生产总览确实有长录制；已核实的长文件没有按六个 subtask 物理拆成六份。

### 4.2 六个 subtask 就是六段区间标注

33809 共 2,599 帧，全部 `episode_index=0`；六段为：

| 段号 | 帧范围（左闭右开） | 秒范围 |
|---|---|---|
| 0 | [0,288) | 0～9.60 |
| 1 | [288,557) | 9.60～18.57 |
| 2 | [557,902) | 18.57～30.07 |
| 3 | [902,1514) | 30.07～50.47 |
| 4 | [1514,2142) | 50.47～71.40 |
| 5 | [2142,2599) | 71.40～86.63 |

`subtasks.jsonl` 保存边界和文字，Parquet 的 `subtask_index` 表示每帧归属，`source_segments` 保存源/输出映射。原始五个 marker 与五处分界对齐后吻合，支持按打点分段的解释；打点是采集按键、自动产生还是事后整理，尚未核实。

六段文字相同，均为“取物、调整条码朝向、放到扫描位置”，`atomic_action` 都为 `move`。它们不是六类不同动作，也未逐段证明每段恰好是一轮成功抓取。

### 4.3 我们的 Tag 与它如何对应

| 对象/字段 | 含义与规则 |
|---|---|
| Recording | 保留采集原始时间线及原件 |
| Episode | 管理、审核、交付的一条数据；可来自整段录制或选定窗口 |
| Subtask / 区间 Tag | episode 内的语义范围；默认不创建新 episode、不复制媒体 |
| 我方 `start_step/end_step` | 可映射起止帧，但必须匹配数据版本和时间轴；重采样不能照抄编号 |
| `label/path/attributes` | 对应名称、分类和动作等属性 |
| `annotation_id`、父子关系、对象/关系 | 保留稳定标注身份与完整结构，不能压缩成单个整数编号 |

我方冻结的 episode 切片允许间隙、不允许重叠；Tag 则支持语义父子关系和交叉区间。**六个连续区间 Tag 可以表达对方六段，但并非所有 Tag 都是 subtask。**只将指定“任务分段”轨道导出为逐帧编号，明确重叠、空隙和未标注规则，其余标签完整保留。

`subtasks.jsonl`、`atomic_action` 等属于需约定的扩展，不是所有官方 LeRobot 数据集的必备字段。若要把某个 Tag 真正变成数据条目，另设“从区间创建 episode”，生成新身份并保留父来源。

### 4.4 标注保存和审核差异

| 项目 | 已核实事实 / 建议 |
|---|---|
| 对方 COT | processed 桶另存 `labels/cots/<版本>/cot.json`，关联基础 episode；包含时间段、执行者、动作、接触、结果、置信度及前/中/后状态 |
| 对方 EGO | 另存 `rebuild/<版本>/` 新包；样本前后均 4,373 行，subtask 14→15，593 行分段编号改变，部分 state/action 数值改变；重建算法未知 |
| 对方在线编辑 | 已查手册定位为 COT/EGO 示例查看；当时非 2D 总保存分支为模拟成功。2D 有真实保存 API 路径，但未做写入验收；3D 展示也不等于可编辑空间标注 |
| 我方 | 已有 Tag 编辑、不可变修订、精确提交/审核绑定、冲突及重复请求处理；机器人语义表单、2D/3D 编辑需按需求补齐 |
| 目标 | 保留数据库在线修订，可靠生成不可变标注 JSON；唯一编辑入口，避免数据库与 OSS 文件各自修改 |
| 修改与导出 | 普通 Tag 保存不重写媒体/基础 Parquet；需要逐帧标签列时生成绑定标注修订的派生包，保留基础版本 |

三种状态必须分开：**自动 QC 检查结构/信号，人工数据审核判断采集是否符合任务，标注审核判断标签是否准确。**对方样本 31247 自动报告为 20 pass、1 warn、1 info、3 skip、0 fail，人工通过；warn/skip 不能都显示为“已通过”。

## 5. 官方 LeRobot 读取验证与目录取舍

SRobot 原包为 `v0.2.0`，目录、任务与 episode 元数据不符合官方 reader 预期；仅移动 info 或改版本号不够。本次重组内容与结果：

| 整理项 | 处理与验证 |
|---|---|
| 目录/元数据 | 创建 `meta/`、`data/`、`videos/`，生成 info、stats、tasks/episodes Parquet 和媒体引用 |
| 数值/类型 | 整理向量与列类型；286 行非时间数值列一致；timestamp float64→float32，最大差约 `4.45e-7` 秒 |
| RGB | 六路 MP4 原样复制、哈希相同；指定帧读取和像素对照通过 |
| Reader | LeRobot 0.6.1 官方 reader 与 PyTorch DataLoader batch 读取通过，无需 Lance |
| 未覆盖 | 对方深度已常规解码，但未在该原型中通过官方 depth reader；完整 MCAP 转换器、单位/标定生产适配未完成 |

**原型验证的是 SRobot → 标准文件包，不代表我方主存储已切换。**官方 reader 可读也不代表自动理解我们全部标签、标定或审计扩展。

| 目录选择 | 优点 | 代价与建议 |
|---|---|---|
| 每个 episode 一个完整 LeRobot 根目录 | 直观、可独立读和下载；原型已验证 | 小文件和元数据重复；推荐日常主存储采用 |
| 多 episode 共用官方 v3 分块文件 | 便于大集合组织、减少部分对象开销 | 单条复制未必成完整包；后续用于集合交付 |
| SRobot 式自定义平铺目录 | 文件名直观 | 依赖适配，偏离官方兼容目标；借鉴说明文件，不照搬格式 |

官方 v3 允许多 episode 共用数据/视频文件，[标准格式不等于一条一个文件夹](https://huggingface.co/docs/lerobot/main/porting_datasets_v3#file-organization-v21-vs-v30)。多个单条包合并时，必须整理全局 index、episode_index、task_index、统计和视频偏移，不能直接拼目录。

## 6. UI：值得学习什么、保留什么

### 6.1 场景对比与改进

| 场景 | 对方表现 | 我们现状 | 建议 |
|---|---|---|---|
| 生产进度 | 围绕总览、任务、采集、审核组织 | 相关能力已有，分布在上传、切片、数据集、标注等入口 | P0：同一批数据按生产阶段串联，点击状态到对应待办 |
| 查看文件 | 审核记录旁直达 OSS 目录、预览和下载 | 原始浏览器已有；标准包、来源、标签分散 | P0：episode“文件”页签列齐媒体、数值、标注、说明和报告 |
| 来源关系 | 元数据有映射，单看时长容易误判 | 有录制/episode 关系，但技术身份较多 | P0：并列原始时长、源窗口、episode 时长、帧数、子任务数 |
| 数据审核 | 任务要求、多视频、QC 报告和决定集中 | QC、问题数据、标注审核分散 | P0：单条审核视图，三个审核状态分别展示 |
| 质量可视化 | 有机器人状态投影等结果 | 已有机器人场景和关节曲线 | P1：增加经标定/同步验证的投影和异常定位；无法生成时说明原因 |
| 语义展示 | COT 步骤卡片含执行者、动作、结果与状态变化 | Tag 树/时间轴完整，专门语义解释较少 | P1：现有 Inspector 增加结构化表单与步骤列表 |
| 编辑闭环 | COT/EGO 保存能力未证实 | 有编辑、修订、提交、审核、返工队列 | P0：保留我们的闭环，不用只读展示替代编辑 |
| 切片操作 | 未核实完整采集切片 UI | 已有拖拽、I/O 定位、边界检查、草稿/确认 | P0：明确“创建 episode”和“添加 Tag”是不同动作 |
| 下载交付 | 当前文件下载就近，批量能力未完整验证 | 已有三阶段导出、多选 episode 和任务列表 | P0：保留批量页，补单条“下载标准包/带标注下载” |
| 版本理解 | 有标注版本选择 | 部分页面直接显示 Lance、Dataset 技术名 | P0：主界面用“数据版本/标注修订”；底层路径、哈希放详情 |
| 导航 | 业务集中，但也有嵌套和较长任务列表 | “数据标注/标注任务”等职责需辨别 | P1：统一标注中心，资产、权限、运维归管理区，保留权限边界 |
| 工作区 | 多视角配步骤条 | 共享 Viewer、机器人场景、曲线和多轨时间轴 | P1：视频/时间轴优先，侧栏可收起，步骤列表独立滚动 |

UI 判断基于对方实看页面/截图、我方源码与既有验收，**不是同条件性能或整体视觉排名**。不把截图黑边/长页面当作常规布局缺陷，也不以历史 Mock UI 通过项替代真人验收。

### 6.2 目标页面和验收

建议导航：**生产总览｜采集与原始录制｜数据管理｜标注中心｜导出任务｜系统管理**。所有数据列表能进入统一 episode 详情：

```text
任务 / 机器人 / 日期 / Episode 名称
数据版本 · 标注修订 · 自动QC · 人工数据审核 · 标注审核
父录制及总时长 → 源时间窗 → 当前 episode 时长 / 帧数 / 相机数 / 子任务数
[回放与分段] [数据文件] [数据质检] [标注与审核] [版本与来源]
任务要求/条目列表 ｜ 多视角视频 + 共享时间轴 ｜ 当前段内容/问题
[查看原始录制] [下载标准包] [带标注下载] [进入标注/审核]
```

文件默认按数值、视频、深度、标注、说明、报告分类，可展开真实路径/大小/校验值。名称用于展示、ID 用于关联，改名不搬文件。普通时间显示秒，精确编辑展开帧号，明确编号起点和结束是否包含。

标注共用一份数据，提供“步骤视图”和“完整标签视图”：前者突出边界、执行者、对象、动作、结果；后者保留层级、交叉区间、属性和关系。普通用户无需理解 OSS Key、Lance 或内部处理阶段。

验收重点：从详情直接辨认父来源与六段关系；列表到文件/下载最多两次页面跳转；标签刷新后内容和修订一致；审核意见直达对应标签区间；上传/处理/文件生成/权限失败可辨别；1440/1024 宽度与键盘下视频、时间轴、保存状态可用。真实多相机首帧、seek、同步误差、掉帧需测量，不预设未经验证的性能结论。

## 7. 目标方案与需求清单

### 7.1 文件和处理契约

```text
raw/<日期>/<机器人ID>/<recording_id>/
  原始 MCAP、视频、配置、manifest

episodes/<日期>/<机器人ID>/<任务ID>/<episode_id>/
  v0001/                          # 完整单 episode LeRobot 根目录
    meta/info.json、stats.json、tasks.parquet
    meta/episodes/chunk-000/file-000.parquet
    data/chunk-000/file-000.parquet
    videos/<camera_key>/chunk-000/file-000.mp4
    hc/                           # 我方扩展，非官方必需
      source.json、source_frames.parquet（按需）
      modalities.json、calibration.json
      conversion_report.json、quality.json、manifest.json
  annotations/v0001/r0001.json、r0002.json

collections/<集合ID>/<版本>/manifest.json
```

目标流程：**原件上传即可独立查看/下载 → 整段或选窗口创建 episode → 解析、对齐、QC、写 LeRobot → 完整校验后提交版本 → 数据审核、Tag 编辑/审核 → 下载标准包或指定标注包。**“直接转 LeRobot”省去 Lance 主存储，仍需数据处理；不强制固定 10 秒或先裁短 MCAP。

集合 manifest 仅是索引，不自动成为官方可读的大数据集；批量交付另组织标准集合包。“带标注下载”必须带上指定修订文件，不能只提供数据库链接。

| 必须保留的契约 | 具体内容 |
|---|---|
| 来源与数值含义 | 原始对象/哈希、recording_id、源时间窗、时钟、帧数、处理器版本；重采样/丢帧/重复帧映射；state/action 顺序、单位、绝对/增量、观测控制时间关系、有效性、标定、深度单位 |
| 数据提交 | 新版本路径写完并校验后再更新可见指针；多文件上传不是原子目录事务，不依赖目录重命名 |
| 标注一致性 | 修订绑定数据版本/内容哈希/Schema；数据库修订通过可靠任务生成文件，失败可重试；“已保存”与“文件已就绪”分开 |
| 媒体与读取 | 编码/时间契约一致时复用；切片需正确解码与定位，非关键帧边界可能转码；Parquet 查询、媒体索引和缓存承接必要帧读取 |
| 迁移范围 | `lance_commit`、`StepReaderPort`、目录索引、`base_lance_version`、导出及历史引用一起迁移；仅改 exporter 不够 |

## 8. 实施顺序与待决策项

| 阶段 | 交付与完成条件 |
|---|---|
| A：定契约 | 包布局、来源映射、版本绑定、深度/action；选我方真实短录制、长录制和已有导入包作为验收集 |
| B：新主流程 | 不写新 Lance，打通标准包、读取、Tag、下载；数值/RGB/深度/来源/标签核对通过 |
| C：UI 和交付 | 聚合详情、三种状态、版本化标签包；采集员/标注员/审核员完成真实任务 |
| D：迁移切换 | 历史迁移、兼容读取、回退；旧审核可追溯，引用迁完再回收 Lance/媒体 |
| E：效率优化 | 根据实测增加语义表单、投影、集合包、缓存与对象数量优化 |

UI 设计可与 A/B 同步；每阶段必须交付可运行结果，不能只完成按钮。主要成本是原始与 episode 媒体重复、小文件开销、Lance 契约迁移，以及时间变换后的标签映射。锁定 reader/格式兼容矩阵，升级先验；UI 优先改信息和操作，不以全面换主题为目标。

| 需评审的决策 | 推荐默认值 | 调整条件 |
|---|---|---|
| 单条可读 vs 集合效率 | 独立 episode 优先，集合后补 | 对象数/读取成本成为实测瓶颈 |
| 标注主存储 | 数据库管理修订，可靠生成文件快照 | 明确需要脱库、多用户离线编辑，并补冲突合并 |
| 何时生成独立媒体 | 边界确认后、标准版本提交前 | 临时预览切片可只保留时间窗 |
| 短录制是否手工再切 | 完整任务整段创建 episode | 首尾无效或任务边界不明确 |
| subtask 是否全覆盖 | 主分段轨道明确覆盖/未标注规则，其他 Tag 自由标注 | 并行动作需保留多轨、多标签 |
| COT/2D/3D 投入顺序 | 先区间 Tag 与机器人语义字段 | 有明确框、Mask、3D 交付需求 |
| 原始录制保留期 | 先保留，再定生命周期 | 已量化规模、重处理及追溯需求 |
