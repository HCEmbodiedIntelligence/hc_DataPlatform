# P01–P20 前端增量改版与效果图计划

> 计划状态：前端方向已形成初稿，等待效果图评审后形成实施版
>
> 编制日期：2026-08-17
>
> 本文件只定义前端信息架构、交互、页面复用和效果图工作，不代表真实 API、数据库或 Worker 已完成。后续实施计划必须继续以代码、OpenAPI、测试和验收结果为准。

## 1. 目标与边界

本轮不完全推翻现有页面，而是在保留可复用布局、表格、筛选器、详情抽屉和工作台框架的基础上，修正业务概念、操作路径、权限表达和数据可视化复用方式。

目标如下：

1. 使 P01–P20 与机器人遥操作、采集、上传、质检、Lance 转换、标注、清洗、审核、发布和治理的实际链路一致。
2. 页面按功能复用，不因内部员工、采集外包、清洗外包、审核员或管理员的身份分别创建重复页面。
3. 权限只控制数据范围、可见模块和可执行动作，不改变核心页面的信息架构。
4. 建立统一的数据可视化工作台，承接 Raw MCAP、Lance、标注、清洗、审核和已发布版本查看。
5. 增加 P20“采集任务”，将采集任务码、人员分派和采集进度从上传记录中分离。
6. 先完成页面效果图并由产品确认，再重写真实 API 实施计划并进入编码。

本轮明确不做：

- 不直接实现后端业务能力。
- 不把 Browser Mock 当作正式 API 合同。
- 不新建“按角色划分”的重复业务页面。
- 不把云端平台置于 PICO、Gateway 与机器人之间的实时控制闭环。
- 不在 P12 增加费用、计费、成本或账单能力。

## 2. 不可违背的业务方向

后续设计与开发必须服从以下四份方向文件：

1. `PICO 跨本体遥操作与机器人端录制方案.md`
2. `VR 全身遥操作初版方案（固定颈部）.md`
3. `统一机械臂规控、遥操作与数据采集平台建设及调试上线方案.md`
4. `数据平台 评测.md`

由上述文件和本轮产品讨论确定的约束如下：

- PICO 负责统一 XR 输入和交互，不在 PICO 端计算机器人关节控制量；机器人适配、IK、限位和安全控制位于机器人侧或 Gateway/Adapter。
- 视频链路采用 WebRTC 等实时链路；云端数据平台不进入实时遥操作控制闭环。
- PICO 可能长期离线，不保存机器人采集数据；PICO 的 `SAVED` 只代表操作侧完成次数，不等于云端已接收或质检通过数量。
- 采集任务码采用带校验的 8 位码，用于任务归类，不是数据唯一标识，也不是访问凭据。
- 机器人接受录制请求时生成 `data_package_id`；重复请求应映射到同一数据包，云端按 `data_package_id` 幂等接收。
- Raw MCAP 不可变；上传支持单次采集完成后上传、任务批量上传和离线硬盘导入。
- 自动质检通过后才进行 30 Hz 对齐并生成 Lance；异常采集条目停留在 Raw，不允许人工覆盖为通过后直接进入 Lance。
- 预览从 Lance 按需生成；标注和清洗采用版本化、非破坏性方式记录，时间区间统一采用 `[start_step, end_step)`。
- 审核与发布分离：审核员可批准、拒绝或要求修改；发布者冻结不可变版本。
- Raw、Manifest 和已发布版本的 Manifest 在 V1 不允许业务删除，只允许归档、分层存储和缓存清理。

## 3. 已确定的账户与权限模型

平台部署在公网，前期由公司内部人员使用，后续允许采集和清洗外包人员使用。因此前端必须从第一版就按公网暴露面设计。

已确定规则：

- 用户名公开注册，V1 不要求邮箱验证和 MFA。
- 注册后账户状态为 `PENDING`，由管理员审批后才能登录业务系统。
- 审批后创建一个私有空项目，并授予该用户只读查看权限；真实业务项目仍由管理员单独授权。
- 项目授权在撤销前持续有效，不设置固定的“内部人员/外包人员”账户类型。
- V1 使用项目隔离，不增加外包供应商组织层。
- 采集人员只能查看分配给自己的任务、自己通过 Web/工作站提交的数据，以及机器人自动上传的汇总进度。
- 清洗人员只能查看分配给自己的任务和预览；默认不能下载 Raw；只能提交审核，不能批准或发布。
- 审核员负责审核，发布者负责冻结正式版本。
- 所有人进入同一个 P01；P01 的模块、数据范围和动作由能力权限决定。

权限实现原则：

- 路由权限决定能否进入功能。
- 数据范围权限决定能看到哪些项目、任务和采集条目。
- 动作权限决定按钮是否显示或是否可用。
- 后端必须再次执行真实权限校验；前端隐藏按钮不能作为安全边界。

## 4. 当前前端的主要不合理点

以下结论来自当前仓库路由、页面、Mock、共享组件和本地页面验证；它们用于指导增量修改，不表示所有页面需要重写。

### 4.1 全局问题

- 当前只有 P01–P19，缺少注册、待审批、审批管理和 P20 采集任务入口。
- 顶部搜索、通知和账户区域外观上可操作，但缺少完整状态或真实行为，容易造成错误预期。
- 多个页面直接展示纳秒时间、字节数、内部枚举和超长内部 ID，缺少面向业务人员的格式化层。
- P08、P09、P14、P19 等页面在 1280 宽度下有整页横向滚动或主要动作被挤出的问题。
- 中英文状态、操作名和技术术语混用；外包用户很难理解 `COMMIT`、`EXCLUDE_RANGE`、原始纳秒等表达。
- 当前部分页面把“列表能显示 Mock 数据”误认为功能可用，真实 API 模式下没有一致的不可用、空数据和错误状态。
- 页面按现有模块各自实现可视区域，Raw、Lance、标注、清洗和审核缺少统一的可视化内核。

### 4.2 业务概念问题

- P01 当前指标偏存储和 Mock 漏斗，没有完整表达采集任务、云端接收、自动质检、Lance、标注、清洗、审核和发布的真实阶段。
- P02 容易混淆“上传来源/连接器”和“机器人/组件注册表”。
- P03 以“新建上传”为核心，缺少采集任务、任务码、机器人数据包和上传幂等上下文。
- P04 缺少 `collection_session_id`、`recording_request_id`、`data_package_id`、Manifest 校验和自动质检的清晰关系。
- P06 的业务对象需要统一命名为“采集条目”，不能与 `data_package_id`、rollout 或 episode 标识混为一谈。
- P09 的人工问题治理容易与 Raw 自动质检异常混在一起；它应主要处理已经进入 Lance 后发现的人工质量问题。
- P11 使用“提交版本/Commit”容易让清洗人员误以为自己可以发布，应该改为“提交审核”。
- P12 仍可能残留费用或成本概念；这些内容必须全部移除。
- P18 固定角色模型与项目级细粒度权限不一致，需要改为权限模板加项目授权。

## 5. 页面复用架构

### 5.1 统一数据可视化工作台

新增一个共享的 `DataVisualizationWorkbench` 设计内核，不按角色创建多个页面。它通过数据适配器、只读/编辑模式和动作能力复用：

| 模式 | 数据来源 | 主要用途 | 允许动作 |
|---|---|---|---|
| Raw 诊断 | MCAP、Manifest、Topic、自动质检结果 | 查看异常采集条目、定位时间段和传感器问题 | 默认只读、跳转、筛选、复制诊断信息 |
| Lance 浏览 | 对齐后的 Lance | 浏览多相机、关节、动作、状态和时间轴 | 只读、筛选、对比 |
| 标注 | Lance + 标注草稿/版本 | P08 标注 | 创建、修改、提交标注草稿，受权限控制 |
| 清洗 | Lance + 质量规则/区间修订 | P11 非破坏性清洗 | 增加排除区间、规则和备注，提交审核 |
| 审核对比 | 原始版本 + 编辑版本 | 审核标注或清洗结果 | 原始/编辑/对比、批准、拒绝、要求修改 |
| 发布查看 | 冻结版本 | 查看已发布数据版本 | 只读、追踪组成和审计记录 |

共享工作台必须统一以下能力：

- 相机布局、时间轴、播放控制、步号/时间显示。
- 关节、动作、状态曲线和光标联动。
- 数据质量标记、异常区间和评论定位。
- 原始、编辑和对比视图。
- 数据格式化、空态、加载、错误、无权限和能力不可用状态。
- 只读与编辑动作由能力开关控制，布局保持一致。

P08 标注页面和 P11 清洗页面只增加各自的工具面板，不复制可视化主体。P01 的异常入口也复用该工作台的 Raw 只读诊断模式。

### 5.2 通用页面模板

建立三类复用模板：

1. 列表页：统一筛选条、保存视图、分页、排序、批量动作、空态和错误态。
2. 详情页/抽屉：统一摘要、关联对象、状态时间线、审计记录和危险动作位置。
3. 工作台：统一左侧对象/任务队列、中部可视化、右侧工具面板和底部时间轴。

### 5.3 响应式范围

- 1440×900 作为主要效果图基准。
- 1280 宽度必须完成核心任务，不能出现整页横向滚动；数据表可以在自身容器内滚动。
- 平板支持列表查看、审批和轻量处理。
- 手机只支持登录、待办、状态和简单审批，不承诺完整标注/清洗工作台。

### 6.1 未编号认证与系统状态页

下列页面是平台基础入口，不占用 P01–P20 编号：

- 登录。
- 用户名注册。
- 注册成功/等待审批。

## 7. P01 的具体改版方向

P01 不再把 Mock 数据结构直接当作正式业务合同。效果图阶段先验证信息架构，后续 API 合同需要根据真实数据库和业务规则单独设计。

### 7.1 建议模块

1. 我的待办：采集、标注、清洗、审核、发布和账户/项目相关待办。
2. 采集与接收：任务进行中、PICO 已保存、云端已接收、等待上传和上传失败。
3. 自动质检：通过、异常、处理中；异常项跳转 Raw 诊断。
4. 数据处理：等待 30 Hz 对齐、Lance 已生成、转换失败。
5. 标注与清洗：待领取、进行中、待审核、需要修改。
6. 发布：待发布、已发布版本和最近冻结记录。
7. 最近活动：只展示用户有权查看的业务事件。

### 7.2 仍需产品确认的指标

- 默认统计范围是“我参与的项目”还是“当前项目”。
- 默认时间范围以及日界线、时区。
- PICO `SAVED` 与云端已接收差异是否作为主告警。
- 自动质检异常的优先级计算方式。
- 待办排序是按截止时间、风险还是业务优先级。
- 跨项目、跨区域是否允许汇总。
- 指标刷新频率和可接受延迟。
- 空数据、部分失败和统计延迟的展示规则。

## 8. 效果图交付顺序

效果图先于业务编码，分四批评审，以减少一次性推翻的成本。

### 批次 A：平台骨架与主链路

- 登录、注册、等待审批、无权限状态。
- 全局导航、项目切换、通知和账户菜单。
- P01、P02、P03、P04、P20。
- 重点验证采集任务、上传记录、数据包、自动质检和 Raw 诊断的边界。

### 批次 B：数据生产工作台

- P05、P06、P07、P08、P09、P10、P11。
- 重点验证统一数据可视化工作台在浏览、标注、清洗和审核模式下的复用。

### 批次 C：治理与机器人资产

- P12、P13、P14、P15、P16、P17、P18、P19。
- 重点验证公网安全、项目授权、容量而非费用、数据不可变和机器人资产关系。

### 批次 D：关键状态图

- 空数据、加载、部分失败、无权限、功能未开放、会话过期。
- 自动质检异常、上传中断、Manifest 校验失败、Lance 转换失败。
- 标注/清洗提交审核、要求修改、审核通过、发布冻结。

每个主要页面至少提供 1440×900 桌面效果图，并检查 1280 宽度。移动端只对认证、待办、状态和轻量审批提供示意。

## 9. 效果图验收标准

- P01–P20 和认证状态均有覆盖，页面编号与功能边界一致。
- 不出现按“内部/外包/管理员”复制的同功能页面。
- P08、P11、审核对比和 P01 Raw 诊断能证明共享同一可视化内核。
- 自动质检异常不会被设计成人工覆盖通过并进入 Lance。
- P12 不出现任何费用、计费、账单、价格或成本组件。
- 1280 宽度无整页横向滚动，主动作无需横向滚动才能看到。
- 业务时间、容量、状态和标识有统一格式化；完整技术值可按需查看。
- 页面明确展示加载、空态、错误、无权限、只读和能力不可用状态。
- 高风险动作具有清楚的权限提示、影响说明和确认步骤。
- UI 不承诺不存在的 API、数据库表、Worker 或实时控制能力。

## 10. 效果图确认后的计划重写

效果图确认后，按以下顺序更新实施计划，保留原计划和审计结论，不覆盖历史信息：

1. 将最终页面字段、筛选、动作和状态映射到现有 OpenAPI 与后端实现。
2. 对无真实 API 支持的 UI 明确标记：需要产品确认、需要技术设计或可以直接编码。
3. 重写 P01–P20 真实 API 覆盖矩阵，补充 P20 和认证流程。
4. 为统一可视化工作台定义前端适配器接口，但不直接把 Mock 类型升级为正式合同。
5. 更新后端生产就绪缺口，加入公网账户、审批、授权撤销、审计和外包数据隔离。
6. 形成按依赖和文件所有权划分的多终端实施提示词。
7. 在实施前重新运行前端类型检查、单元测试和关键页面视觉回归，记录基线。

### 13.1 主设计系统结论

`ui-ux-pro-max` 的首次候选给出了金色/奶油色、Roboto、营销落地页和 GSAP 滚动揭示。根据 `frontend-design` 的通用模板自检以及“增量改版”原则，这些建议未直接采用；只保留高密度、低动效、状态色和可访问性方向。

当前共享基线位于：

- `design-system/hc-data-platform/MASTER.md`

主方向为“机器人遥测账本”，唯一重点视觉元素是编码真实业务阶段与数据血缘的“信号轨道”。配色保留当前紫蓝基调，字体优先系统中文字体，组件继续使用 Ant Design 和现有 Lucide 图标体系。

## 14. 2026-08-17 效果图逐项评审后的覆盖结论

本节保留前文作为历史初稿，并记录用户对 E01–E10 的逐项修订。与前文冲突时，以下结论优先：

- 全站使用仓库原始 `frontend/src/assets/hangcha-logo.png`，不采用效果图生成的六边形 `HC` Logo。
- 用户名和密码直接注册，不审批账户，不验证邮箱或手机号；新账户默认没有项目和业务权限。
- 只有加入项目和权限申请需要审批；P18 不再出现账户审批或自动创建个人私有项目。
- “数据上传”是功能入口，内部复用“新建上传/上传记录”两个 Tab；P04 继续承接单个包的摄取/QC 详情。
- 标注和清洗是同一功能；导航只保留“数据标注”，P11 独立页面取消，旧路由只做兼容跳转。
- P20 不分派人员/PICO/机器人，不设置有效期，不支持暂停/继续。任务由“新建采集任务”抽屉创建，直至显式关闭。
- P20 创建不配置模态/Topic；使用“采集场景”和“任务描述”。相机/Topic 从上传包 Manifest 自动识别。
- 标注工作台同时展示自动发现的相机，但所有视频共用一个时间轴；Tag 编辑必须支持多级路径和属性。
- 审核阶段主要检查 Tag 层级、区间、属性、冲突和 Schema 版本，不重复承担上游一致性验收。
- P12 按 Raw、标注完成、待标注、问题数据展示容量；不展示冷热/中容量。P13 不提供影响模拟。
